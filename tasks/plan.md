# Implementation Plan: Issue-Driven Build Workflow + OpenCode Installer

## Overview

Extend the agent-skills framework so spec → plan → build → PR can be driven from a GitHub Issue, and so the framework installs into OpenCode with two scripts (install + update). Five new commands (`/spec-pr`, `/issue-create`, `/issue-list`, `/issue-build`, `/issue-pr`), four new skills (`spec-pr`, `issue-create`, `issue-list`, `issue-pr`), two shell scripts, one docs update, and a sweep that makes every `CLAUDE.md`-only reference name `AGENTS.md` too. Specs/plans/todos move from the repo root to `specs/<feature>/`. Build-tracking issues use the `[BUILD]` prefix; spec PRs use the `[SPEC]` prefix — both share the same kebab-cased `<name>`.

## Architecture Decisions

- **`specs/<feature>/` is the new convention; repo-root paths are deprecated fallbacks.** Changing the default in `/spec` and `/plan` and extending `/build`'s resolution list keeps existing consumer repos working while pointing new work at the per-feature layout. The spec-driven-development and planning-and-task-breakdown skills are the skills that hardcode these paths, so they are edited in lockstep with the commands.
- **Four new skills, not five.** `/issue-build` is a command that chains the existing `incremental-implementation` + `test-driven-development` skills; it has no unique workflow of its own. `/spec-pr`, `/issue-pr`, `/issue-create`, and `/issue-list` each get a skill because each defines its own workflow.
- **Dual prefixes: `[SPEC]` for spec PRs, `[BUILD]` for build issues.** A spec PR (raised by `/spec-pr`) gets `[SPEC] <name>`; a build-tracking issue (raised by `/issue-create`) gets `[BUILD] <name>`. Both share the same kebab-cased `<name>`, so a spec and its build issue are linked by name and disambiguated by prefix. This avoids the collision where a single `[SPEC]` prefix would appear on both the spec PR and the build issue.
- **Two scripts, not one with a `--update` flag.** `install-opencode.sh` must succeed against a never-installed project (no marker, no symlink, no `AGENTS.md`); `update-opencode.sh` assumes a prior install and is allowed to fail loudly when that assumption is broken. Combining them would force update calls to re-derive install-vs-update mode. Two scripts, two contracts.
- **Installer marker on `AGENTS.md` line 1** (`# Auto-generated by agent-skills install-opencode.sh`) is how the updater detects installer-managed files vs hand-edited ones. Hand-edited files are never overwritten.
- **Kebab-case is the single identity.** `# Spec: Widget 7 new feature` → `[BUILD] widget-7-new-feature` (issue) / `[SPEC] widget-7-new-feature` (spec PR) / `specs/widget-7-new-feature/` (dir). The `<name>` is identical across all three; only the prefix differs.
- **`build` label, created idempotently.** `gh label create build --force` creates or updates the label before `gh issue create --label build`. The `[BUILD] ` title prefix is retained as a secondary signal so `issue-list` can filter on title without needing the GitHub API to resolve labels.
- **`issue-build` resolves spec/plan/todo from the issue body first, falls back to the issue title.** Body links are explicit and survive renames; the title fallback keeps `issue-build` working when the issue body was hand-edited.
- **`issue-pr` references the issue with `Resolves #<n>`** so GitHub links the PR to the issue; merging the PR is still a human action. No auto-close from any command.
- **`spec-pr` raises a PR for the spec/plan/tasks themselves** (not the implementation). The PR title is `[SPEC] <name>`. This is the "merge the spec" step that `issue-create`'s workflow assumes has already happened.
- **Claude Code `.md` commands invoke skills as `agent-skills:<name>`** (per existing convention in `.claude/commands/`); `commands/*.toml` and `.gemini/commands/*.toml` use bare `Invoke the <name> skill.`. The `description` field is byte-identical across all three dirs (enforced by `validate-commands.js`); only the prompt bodies differ in that one prefix.

## Risks and Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| `validate-commands.js` NAME_MAP doesn't recognise new command stems (e.g. `planning` vs `plan` aliasing) | High — CI fails on first new command | The existing NAME_MAP only maps `plan`→`planning`. New commands use identical stems across all three dirs, so no NAME_MAP entry is needed. Verified by reading `validate-commands.js:38-43`. |
| `run-evals.js` trigger evals fail because new skill descriptions don't contain the vocabulary users actually say | Medium — CI fails | Write trigger prompts that paraphrase realistic user asks (e.g. "raise a GitHub issue for this spec"), not copy-paste from the description. If a prompt doesn't rank top-k, fix the description, not the eval (per `evals/README.md` §"Writing good trigger prompts"). |
| `issue-build`'s issue-body link parsing is ambiguous (what counts as a "link to spec"?) | Medium — `issue-build` resolves the wrong path or fails | The skill text specifies: look for markdown links matching `specs/<feature>/SPEC.md`, `specs/<feature>/tasks/plan.md`, `specs/<feature>/tasks/todo.md`. The fallback derives `<feature>` from the `[BUILD] <name>` title and looks under `specs/<name>/`. Document both paths in the issue-build command prompt. |
| `spec-pr` and `issue-create` descriptions collide in trigger evals (both mention "spec" and "PR"/"issue") | Medium — trigger evals fail because one skill outranks the other | Distinguish descriptions: `spec-pr` mentions "raise a PR for the spec/plan/tasks themselves" and "[SPEC] prefix"; `issue-create` mentions "open a GitHub Issue for the build" and "[BUILD] prefix". The prefix vocabulary is the disambiguator. If trigger evals still collide, tighten `top_k` to 1 for each skill's signature ask. |
| `update-opencode.sh` `git pull --ff-only` fails when the repo has local commits | Low — updater exits non-zero with a clear message | Document in `docs/opencode-setup.md` that the updater requires a clean fast-forward; users with local commits should `git stash` or rebase first. The `set -e` + `--ff-only` combination fails loudly rather than creating a merge commit. |
| `install-opencode.sh` symlink is created relative to the script's own repo path, but the target project may be cloned elsewhere | Medium — symlink points to the wrong place | `REPO_SKILLS="$(cd "$(dirname "$0")/.." && pwd)/skills"` resolves the absolute path of the repo the script lives in, regardless of where it's invoked from. Test covers this by running the installer from `/tmp/opencode`. |
| Kebab-casing logic differs between the skill's prose description and any shell test that exercises it | Low — test and skill disagree on edge cases | The kebab-casing rules are specified in SPEC.md §"Name derivation": lowercase, trim, collapse whitespace to single hyphens, strip invalid chars. The shell tests in `issue-create-test.sh` and `spec-pr-test.sh` implement the same rules and assert the documented example (`Widget 7 new feature` → `widget-7-new-feature`). |
| New eval case files reference fixtures that don't exist (`evals/fixtures/<name>/`) | High — `run-evals.js` errors on missing fixtures | `spec-pr`, `issue-create`, `issue-list`, and `issue-pr` are conversation-shaped skills whose evals are `kind: "dialogue"` (no fixture needed, per `evals/README.md` §"Adding a skill"). The eval case JSON files will omit `files[]` or set `kind: "dialogue"` to avoid the fixture requirement. |
| The `agent-skills:` prefix in `.claude/commands/*.md` is forgotten on new commands | Low — Claude Code doesn't auto-invoke the skill | Match the existing convention exactly: `.claude/commands/issue-create.md` opens with `Invoke the agent-skills:issue-create skill.` (verified against `.claude/commands/spec.md:5` and `.claude/commands/build.md:5`). |
| Models treat "mark the task complete" as a mental note, not a file edit — the checkbox in `tasks/todo.md` is never flipped, so iterative reviews can't see which task a commit closed | High — the team loses traceability between commits and tasks; `/build auto` resumes from the wrong task because pending checkboxes never advance | Rewrite the `/build` prompt so the checkbox edit is an explicit, concrete step: "edit `tasks/todo.md` (or `specs/<feature>/tasks/todo.md`), change `- [ ]` to `- [x]` for this task, stage that file alongside the code, commit together." Remove the separate "mark complete" step entirely — there is no separate step, the edit is part of the commit. Mirror the same language in the `incremental-implementation` skill's Increment Checklist. The `/build auto` "Stage only the files that task touched plus its task-status update" line already implies this, but "task-status update" is too abstract for many models — spell it out as "the `- [ ]` → `- [x]` edit in the todo file." |
| A model uses `[SPEC]` for a build issue or `[BUILD]` for a spec PR, breaking the disambiguation | Medium — `issue-list` misses the issue (it filters on `[BUILD] `); team confusion | The `issue-create` and `spec-pr` command prompts hardcode the prefix in the `gh` command (`--title "[BUILD] <name>"` / `--title "[SPEC] <name>"`). The skill descriptions name the prefix explicitly. The "Never do" boundary in SPEC.md forbids mixing the two. |
